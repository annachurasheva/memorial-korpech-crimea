# РЕГЛАМЕНТ ФОРМИРОВАНИЯ КАРТОЧКИ ПЕРСОНЫ (РЕЖИМ 03)

**Проект:** Memorial Korpech Crimea
**Стек:** Astro (SSG) / EdgeOne Pages / Node.js
**Философия:** Карточка персоны — это не статичная запись, а **узел памяти**, вокруг которого формируются связи: сослуживцы, места захоронений, родственники, поисковики.

---

## 1. ВИЗУАЛЬНОЕ ВЫДЕЛЕНИЕ МЕСТ ЗАХОРОНЕНИЯ

### 1.1. Первичное захоронение — отдельный смысловой блок

Первичное захоронение **не должно быть просто строкой в таблице**. Это критически важная историческая информация, которая требует визуального акцента и навигации.

**Реализация в Markdown:**
```markdown
## Место первичного захоронения

> [!IMPORTANT] Первичное захоронение
> **Крымская АССР, Ленинский р-н, выс. 66,3, северо-восточные скаты, 400 м**

*Это временное место, где павшие были сложены во время боевых действий. Дальнейшая судьба останков требует уточнения.*

🔗 [Все похороненные на выс. 66,3](/tags/burial-vys-66-3/)
```

**Техническая реализация:**
- Используется блок примечания `> [!IMPORTANT]` для визуального выделения.
- Внизу добавляется **ссылка на тег** (автоматически сгенерированная страница списка), где собраны все бойцы, похороненные в этом месте.
- Скрипт-конвертер автоматически создает тег вида `burial: крымская-асср-ленинский-р-н-выс-66-3` и добавляет его в Front Matter.

### 1.2. Текущее захоронение — с возможностью обновления

Если есть документально подтвержденное перезахоронение (например, мемориал Корпечь), это указывается **отдельным блоком**:

```markdown
## Место текущего захоронения

> [!NOTE] Перезахоронение
> **Мемориал Корпечь, Крым**

*Останки были перезахоронены местными жителями или в ходе послевоенных работ.*

🔗 [Все похороненные на мемориале Корпечь](/tags/burial-memorial-korpech/)
```

**Если данных о перезахоронении нет:**
```markdown
## Место текущего захоронения

> [!WARNING] Требуется уточнение
> Данные о перезахоронении отсутствуют.

*Если вам известна судьба останков, пожалуйста, оставьте комментарий ниже.*
```

## 2. ИСТОРИКО-ДОКУМЕНТАЛЬНЫЙ КОНТЕКСТ (Почему это важно)

### 2.1. Многослойность данных

Карточка должна отражать **историческую реальность**:

1. **Первичное захоронение** — временное место во время боев (часто — просто поле у высоты).
2. **Отступление** — часть могла отойти, и точные координаты утеряны.
3. **Местные жители** — перезахоранивали из человеческого отношения (не все задокументировано).
4. **Поисковые работы** — идут сейчас, не всех верифицируют (записки в медальонах стираются).
5. **Мемориалы** — возводились без доступа к архивам в/ч (данные были засекречены).
6. **Современные архивы** — сейчас выложены сканы рукописных журналов выбытия, где павший диктовал, кому отправить похоронку.
7. **Похоронки** — не все нашли адресата, не все были отправлены.

### 2.2. Отображение в карточке

Этот контекст **не нужно явно прописывать в каждой карточке** (это раздует объем). Вместо этого:

- В блоке "Первичное захоронение" добавляется **краткая сноска** (как в примере выше): *"Это временное место... требует уточнения"*.
- В блоке "Текущее захоронение" — аналогично: *"Останки были перезахоронены..."* или *"Данные отсутствуют"*.
- **Полный исторический контекст** размещается на отдельной странице "О проекте" или "Как читать карточки".

## 3. СИСТЕМА "БРОНИ" ПЕРВОГО КОММЕНТАРИЯ

### 3.1. Концепция

Под каждой карточкой персоны **должен быть зарезервированный первый комментарий от администрации**. Это не техническая фича Astro, а **организационный процесс**.

**Цель:**
- Задать тон обсуждения (уважительный, исторический).
- Предоставить дополнительный контекст (если есть).
- Призвать родственников/поисковиков откликнуться.

### 3.2. Шаблон первого комментария

```markdown
**Администратор мемориала** · [дата]

Эта карточка создана на основе документа [тип документа] №[ID] из архива [архив].

**Дополнительная информация:**
[Если есть — краткая историческая справка о подразделении, месте захоронения, обстоятельствах гибели.]

**Призыв к родственникам и поисковикам:**
Если вы располагаете дополнительной информацией об этом человеке (фотографии, письма, сведения о перезахоронении), пожалуйста, оставьте комментарий ниже. Мы верифицируем данные и обновим карточку.

*Источник: [ссылка на ОБД Мемориал или иной архив]*
```

### 3.3. Техническая реализация

**Вариант A (Ручной):**
После генерации карточек администратор вручную оставляет первый комментарий под каждой через интерфейс Giscus/Waline.

**Вариант B (Автоматизированный — рекомендуется):**
Скрипт-конвертер генерирует не только `.md` файлы, но и **файл с шаблонами комментариев** (`comments_draft.json`), где для каждой карточки указан текст первого комментария. Администратор затем копирует их в систему комментариев.

**Вариант C (Полуавтоматический):**
Скрипт создает отдельную папку `docs/comments/`, где для каждой карточки лежит `.md` файл с текстом первого комментария. Администратор использует эти файлы как заготовки.

## 4. ЖЕСТКАЯ ПРИВЯЗКА ID К ПЕРСОНЕ (Архитектурное требование)

### 4.1. Критическая важность

ID персоны (`abbrlink`) **должен быть навсегда привязан к `document_id` из архива ЦАМО**. Это не просто техническое удобство — это **вопрос целостности памяти**.

**Почему:**
- Встречаются переписки из разных стран по поводу одной персоны.
- Все родственники должны иметь возможность общаться в **одном месте**.
- Если URL изменится, все внешние ссылки (из форумов, соцсетей, поисковых отчетов) сломаются.
- Поисковики будут ссылаться на конкретные карточки — URL должен быть стабилен.

### 4.2. Алгоритм генерации `abbrlink`

**Правило:** `abbrlink` формируется **только** из `document_id` (или комбинации `document_type` + `document_id`).

**Пример:**
```yaml
# CSV: document_type = "ЦАМО", document_id = "506255127"
abbrlink: camo-506255127
```

**Запрещено:**
- Использовать ФИО в `abbrlink` (может измениться при уточнении).
- Использовать транслитерацию имени (могут быть ошибки, тезки).
- Менять `abbrlink` после публикации карточки.

### 4.3. ЧПУ для людей (опционально)

Если вы хотите человеко-понятный URL, можно использовать **комбинированный формат**:
```yaml
abbrlink: avdeev-grigoriy-iosifovich-506255127
```
Но **якорем стабильности** остается `document_id`. Если ФИО уточнится, `abbrlink` **не меняется** (иначе сломаются ссылки).

## 5. ГЕОГРАФИЧЕСКИЙ И СОЦИАЛЬНЫЙ КОНТЕКСТ

### 5.1. География портала

Портал охватывает территорию **10-12 км от координаты мемориала Корпечь**. Это означает:

- Все первичные захоронения в этом радиусе должны быть **взаимосвязаны**.
- Карточки должны позволять навигацию по географическому признаку.

**Техническая реализация:**
- В Front Matter добавляется тег `geo: korpech-12km`.
- В блоке "Первичное захоронение" указывается **расстояние до мемориала Корпечь** (если известно).
- Создается отдельная страница "Карта захоронений" (на основе тегов).

### 5.2. Работа с поисковиками (пост-запуск)

После запуска проекта планируется **уведомление поисковых отрядов** с просьбой присылать списки по персонам.

**Требования к системе:**
1. **Стабильность URL** — поисковики будут ссылаться на конкретные карточки.
2. **Возможность обновления** — если поисковики присылают новые данные, карточка должна быть обновляема без изменения URL.
3. **Верификация** — обновления должны помечаться (например, "Обновлено [дата] на основе данных поискового отряда [название]").

**Реализация:**
- В Front Matter используется поле `updated` (уже поддерживается темой).
- В теле карточки добавляется блок:
  ```markdown
  > [!NOTE] Обновление
  > **[Дата]**: Данные уточнены на основе сведений поискового отряда "[Название]".
  ```
